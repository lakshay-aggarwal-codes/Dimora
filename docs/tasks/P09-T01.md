## Behaviour
- **Tabs** (each booking in exactly one): Upcoming = confirmed with check-out after today; Pending = host has not answered and the hold is still running (soonest deadline first, with "the host has until ..."); Past = completed, or confirmed whose check-out has passed (so a stay shows as past even before the sweeper marks it completed); Cancelled = declined, expired, cancelled by either side, and a request whose hold ran out but the sweeper has not expired yet. "Today" is the date in Asia/Kolkata.
- **Confirmation page:** reference (`DIM-` + last 8 characters of the id), status, check-in/out with weekday and the listing's times, nights, guests, the stored breakdown lines (same wording as the quote panel) and total, average per night, the house rules and cancellation terms as they were when booked (snapshot, not the live listing), "payments are simulated" note, a link to the live listing when it still exists.
- **Revealed only after confirmation:** the host's name, email and profile link (guest viewer only) and the exact address with a map link (from the private point, `geometry`). For a pending, declined, expired or cancelled booking none of it is in the page or in the data the view receives (a test checks the serialised data does not contain them).
- **Who may open it:** guest, host, admin. Everyone else, a booking that does not exist and a malformed id (`not-an-id`, 23 characters, ...) get the identical 404 and the database is not asked for the malformed ones. A suspended guest is refused. `Cache-Control: no-store` (contact details and an address).
- A host or admin who opens a booking sees the guest's name instead of the host block.
- Every text from a snapshot is escaped (tests with `<script>` and `<img>` in title and rules).
- A booking whose listing was removed still renders from its snapshot.
