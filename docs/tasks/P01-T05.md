# P01-T05 — Repair listing create and edit (Q9) — D-02, D-03, D-11

Date: 2026-10-14 · Node v22.22.2 · No new dependencies.

## Root causes (from docs/BASELINE.md)
- D-02: `POST /listings` had no multipart parser, so `req.body` was undefined and validation crashed.
- D-03: edit read `req.body.listing.image.url`, but the file input is not part of the body.
- D-11: an empty geocoder result threw `TypeError` on `features[0].geometry`.

## What changed
| File | Change |
|---|---|
| `src/routes/listing.js` | POST: `isLoggedIn → upload.single → validateListing → requireImage → geocodeListing → uploadToCloudinary → createListing`. PUT: `isLoggedIn → isOwner → upload.single → validateListing → geocodeListing → uploadToCloudinary → updateListing`. The multipart form is parsed first; the Cloudinary upload happens only after validation and geocoding succeed, so a rejected submission leaves no orphaned image. |
| `src/middleware/listing.js` (new) | `requireImage` (400 "Please choose an image for your listing."); `geocodeListing({backTo})` sets `req.geometry`, and on "not found" or outage flashes a message and redirects back to the form (`/listings/new` or `/listings/:id/edit`). On edit it geocodes again only if location or country changed, or the stored listing has no coordinates (old data). |
| `src/services/geocoding.js` (new) | `geocodeAddress({location, country})` → GeoJSON Point. Query is `"<location>, <country>"` (the country makes the match more precise). Errors: `LocationNotFoundError` (400, no/invalid result, never calls Mapbox for an empty query) and `GeocoderUnavailableError` (503, keeps the cause, message does not echo it). A missing/invalid Mapbox token is not swallowed (500). `getGeocodingClient` moved here; `initGeocoding` in the controller still re-exports it for `server.js`. |
| `src/middleware/index.js` | `isOwner`: missing listing → `NotFoundError` (404); listing without owner → treated as not owned (redirect with message); leaves the listing on `req.listing`. `validateListing`: validates `req.body ?? {}` (no crash without a body) and replaces `req.body` with the cleaned value (trimmed text, numeric price). |
| `src/validation/index.js` | Strings are trimmed (a blank title/location is rejected); `listing.image` removed from the schema, so a text field named `listing[image][url]` is a 400 — the image comes only from the uploaded file. |

| `src/errors` | unchanged; uses `ValidationError`/`NotFoundError`/`AppError` from Q7. |

## Behaviour changes
- A bad place name or Mapbox outage on create/edit returns to the form with a message instead of a 500; other validation errors are still the 400 page.
- Submitting a text value for the image field is rejected.
- Editing/deleting a listing that does not exist is a 404 page (was a 500).

## Manual check (once, with real keys — DoD+)
1. `npm run dev`, log in, open `/listings/new`.
2. Create a listing with a PNG/JPEG, a real place (e.g. "Goa", "India"): expect redirect to `/listings`, the image visible in your Cloudinary `dimora_DEV` folder and the listing on the list.
3. Try a nonsense location (`Qwxzqwxz`): expect to land back on the form with "We couldn't find that location…", no new listing, nothing new in Cloudinary.
4. Edit the listing without choosing a file: it saves and keeps the image.
5. Edit it with a new image: the page shows the new image, and the old one is gone from Cloudinary.
6. Delete the listing.

## Limitations / notes
- Deleting a listing does not delete its image yet (media service in P04-T03). `isReviewAuthor` still crashes for a missing review (D-10, second half) — not in this card.
- The seed script still creates listings without `geometry` (P01-T06); such listings are geocoded the first time they are edited.
- Upload happens before the database save; the clean-up on a failed save is best effort.
