## Behaviour
- Weak or invalid signup: redirect to `/signup`, one alert with all problems, nothing saved. Messages never contain Joi/driver/Mongoose/passport text.
- Duplicate email: "We couldn't create an account with those details. If you already have an account, log in instead." Taken username: its own message (usernames are public anyway).
- Login failure (unknown user, wrong password, locked, too soon, deleted, missing fields): "Incorrect username or password. After several failed attempts an account is locked for a while."
- Suspended account with the correct password: "This account is suspended. ..." and not logged in. A wrong password for a suspended account gets the neutral text.
- Lockout: failures slow the next attempt down; at 10 failures even the right password is refused until 15 minutes after the last attempt; a correct login resets the counter.
- Session id changes at login (tested), so a pre-login id is useless afterwards.
- `next=//evil.com`, `https://...`, `/\evil.com`, `javascript:`, CR/LF, NUL, over-long values all fall back.

## Limitations / deviations
- Roadmap says "fall back to `/`": the helper's default is `/`; the login controller passes `/listings` (what `/` redirects to, and what the existing tests expect).
- Lockout is per account (plugin behaviour), so someone who knows a username can keep it locked by retrying; the 5-per-15-min per-IP login limit (P01-T09) still applies first.
- Usernames remain case-sensitive; the unknown-username path skips the password hash (small timing difference). Neither is in this task's scope.
- The lock message is deliberately the same as the wrong-password message, so a real user who is locked sees no explicit "locked" text beyond the general sentence.
- Password reset / email verification: P02-T05 (optional, Q86).
