## `create({ guest, listing, in, out, guests, expectedTotalMinor?, idempotencyKey })`
Returns `{ reservation, created }`. Order: validate input → replay lookup → load listing (must be public, with a host) → not the host's own listing → rules → quote → compare `expectedTotalMinor` → hold nights in the ledger → re-read the listing (host may have unpublished meanwhile; if so release and 404) → insert the reservation (release the nights if that fails) → return.
- `instantBook` → `confirmed`, no hold. Otherwise `pending` with `holdExpiresAt = now + 24 h`, carried by the ledger rows too.
- Idempotency: the same `(guest, key)` returns the original with `created: false`. The same key with a different listing, dates or guest count is a 409 `idempotency_key_reused`. A double click is handled: the second request loses the night race, waits briefly for the first one's reservation and returns it; if both reach the insert, the unique index decides and the loser releases nothing of the winner's (nights are keyed by the reservation id).
- Errors: 400 bad input/rules, 403 own listing or suspended guest, 404 not bookable, 409 `nights_unavailable` / `price_changed` / `idempotency_key_reused`, 422 listing cannot be priced.

## `transition(reservationId, to, { actor, by, reason, now })`
Checks the table and the actor, then updates with compare-and-set (`status` must still be what was read) and appends to `statusHistory`. Extra conditions: `confirmed` needs a hold that has not run out (`hold_expired`), `expired` needs one that has (`hold_active`), `completed` needs the check-out date to have passed in the listing's zone (`stay_not_over`). A lost race is a 409 naming the status that won. Afterwards: `confirmed` clears the nights' hold; declined/expired/cancelled release the nights; `completed` keeps its (past) rows (ADR-004 "past rows kept"). Whether the *caller* may act (is this user the host?) is the caller's job (P09 policies).

## Invariants (helper `findViolations`)
(a) a night has one owner; (b) pending/confirmed/completed reservations have exactly their nights, in their listing; (c) no ledger row for a released or missing reservation; (d) pending has a hold (same on its rows), confirmed has none. Every unit test ends with it; the DB tests call `checkDatabase()`.

## Deviations and limitations
- Booking rules are the minimum (booking window, min/max nights, capacity) and live in `create`; P07-T06 should move them into one rules module and add advance notice and the same-day cut-off.
- `completed` keeps its ledger rows while the roadmap invariant for P07-T08 says no row belongs to a "terminal" reservation: decide there (delete the rows on completion, or exclude `completed` from the check).
- Nothing calls `create`/`transition` from a route yet; there is no policy `reservation:*` yet.
- No sweeper: a pending request past its hold stays `pending` until something transitions it (P07-T07), although its nights are already takeable by the next request, which then leaves the old reservation without nights until the sweeper expires it (the `(b)` invariant is briefly false in that case; documented in the last DB test).
- Accepting is checked against the hold, then the nights' hold is cleared in a second step; if the hold ran out in that instant another guest could take the nights. Narrow, and a transaction would close it (optional hardening, ADR-004).
