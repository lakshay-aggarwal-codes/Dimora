## Workflow
- Triggers: push to `main`, every pull request. `permissions: contents: read`; a newer run on the same ref cancels the older one; 20-minute timeout.
- Steps: checkout → `actions/setup-node` with `node-version: lts/*` and npm cache → restore/save the MongoDB binary cache → `npm ci` → `npm run lint` → `npm test -- --ci --runInBand` → `npm audit --audit-level=high` with `continue-on-error: true` (report only, never fails the build).
- MONGOMS cache: `MONGOMS_DOWNLOAD_DIR` points to `.mongoms-cache` in the workspace (outside `node_modules`, which `npm ci` deletes). Cache key = OS + hash of `package-lock.json` (the library version decides which mongod it downloads); restore-key falls back to the newest cache for the OS.
- `--runInBand`: each database suite starts its own mongod; on a cold cache parallel workers would download the binary at the same time.
- Node `lts/*` satisfies `engines` (>=20.19.0).

## Limitations
- CI is green only if `package-lock.json` matches `package.json`. P01-T09 added `helmet` and `express-rate-limit` without regenerating the lockfile; if you have not run `npm install` and committed the lockfile since, `npm ci` will fail in CI.
- Action versions (`checkout@v4`, `setup-node@v4`, `cache@v4`) were chosen from memory; newer majors may exist. Dependabot or a manual bump can update them.
- No Prettier check in CI (Prettier has never been run on the code base yet). The README badge belongs to P19-T01.
- "CI green on main" can only be confirmed after you push.

## Owner steps
1. Make sure `package-lock.json` is committed and in sync (`npm install`, then `npm ci` locally).
2. Push to `main` (or open a PR); open the Actions tab and check the `CI` run. The first run is slower (mongod download); later runs use the cache.
3. Paste any failing step's log if something breaks.
