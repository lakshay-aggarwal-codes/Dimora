## Behaviour
- **List.** Only conversations that already have a message; newest message first; 20 per page (`/messages?page=2`). Unread is shown by a dot *and* "N unread" text *and* bold name, never colour alone. Preview is plain text, one line, cut by CSS. Mobile: the same single column (no side-by-side panes); rows stack name, listing and preview and keep the time and badge to the right.
- **Thread polling.** First ask 15 seconds after the page loads (the server already drew it), then every 15 seconds while the tab is visible; a hidden tab asks nothing and asks at once on return. The newest 50 messages are fetched; the list is redrawn only when the message ids differ; text goes in with `textContent`. A 401 or 404 stops it for good; a failed or unusable answer keeps what is shown and tries again. Each ask also clears the reader's unread mark (the API does that for an open thread). An older page (`?before=`) is static. Without JavaScript the page and the reply form work as before; a reload shows new messages.
- Sending still posts the form and reloads the page; scrolling to a new message happens only when the reader is already near the bottom.

## Limitations
- No unread count on the "Messages" menu item; the bell counts notifications only. A messages badge would need its own count endpoint and polling (not in the card).
- Polling, not WebSockets (as the roadmap says). A new message can take up to 15 seconds to appear.
- Two-pane desktop layout was not built; list and thread are separate pages.
- A poll while the thread is open marks messages read even if the reader is scrolled away from them.
- Notifications for new messages are not created (P11-T04 lists no such event).
