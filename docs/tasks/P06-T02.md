# P06-T02 - Approximate public location (Q40)

Date: 2026-10-18 - Deps: P04-T01 (done). **One migration: `007-listing-public-geometry`.** No new dependency, no new environment variable.

## What changed
| Item | Notes |
|---|---|
| `src/utils/geo.js` | `approximatePoint(geometry, listingId)`: the precise point moved by a great-circle step of 300 to 800 m. Direction and distance come from `HMAC-SHA256(secret, "offset\|" + id)` (two 48-bit numbers). Coordinates are rounded to 5 decimals (about 1 m); the step is drawn from 301 to 799 m so the rounded point is still within 300 to 800 m. Also `publicPointOf(listing)`, `distanceMeters`, `configureLocationSecret`, `offsetFor`. |
| Why a secret | The id is in the URL. An offset computed from the id alone could be computed by anybody and subtracted again, giving back the precise point. With the HMAC key (the session secret plus a fixed label, set in `createApp`), the offset cannot be known from outside. In production a missing secret is an error; development and test fall back to a fixed key. Changing `SESSION_SECRET` changes every public point. |
| Model | `publicGeometry` is recomputed by a `pre("validate")` hook on every save (set when it differs, removed when there is no usable precise point). `2dsphere` index `publicGeometry_2dsphere` (migration 007 builds it). Updates that skip `save()` must set the point themselves; the seed saves each seeded listing once. |
| Detail page | `src/controllers/listing.js` passes `publicPointOf(listing)` as `mapPoint`. The precise point is never given to the page; `address.line1` and `postalCode` are printed only by host views (wizard review, location step, edit page, confirm page). |
| `src/services/locationAccess.js` | `mayViewPreciseLocation` / `preciseLocationFor`: host, admins, and a guest whose reservation of this listing is `confirmed` or `completed` (pending, held, expired, cancelled and rejected do not count; neither does another guest's or another listing's reservation). Pure; the trip page (P09-T01) will call it. |
| Migration 007 | Computes the public point for every listing with a precise point (or removes a stale one) and builds the index. Uses the app's own `geo.js` (not a frozen copy) so it equals what a save computes; needs `SESSION_SECRET`. `down` drops the index and the points. |
| Tests | Unit: `geo` (distance range over 3000 ids, determinism, all directions, secret dependence, poles, antimeridian), `locationAccess`, `publicGeometryMigration`, additions to `listing.model`. Page: `listings.publicLocation` (the page source contains none of the precise coordinates or the street address, for many listings; same point on every load). DB: `listing.publicLocation.db` (stored point, `$near` on the index, address change moves the point, anonymous / other member / host see no precise data on the detail page, home, search and "My listings", migration). Two older show tests now expect the approximate point. |

## Acceptance
"Addresses of unbooked users are not recoverable from page source": the page tests search the rendered HTML for the precise coordinates (several formats) and the street address and postal code and find none; the map point is 300 to 800 m away and keyed, so it cannot be reversed from the id.

## Limitations
- A listing written before the wizard may keep a street address in its old free-text `location`, which the detail page still prints; the wizard and the edit sections store only "city, state" there.
- The trip page does not exist yet, so the guest-of-a-confirmed-reservation case is tested at function level (`locationAccess`), not through a page. P09-T01 must call `preciseLocationFor`.
- 300 to 800 m is a privacy margin, not secrecy against a determined person with many listings of the same host at known spots; it matches the roadmap.
