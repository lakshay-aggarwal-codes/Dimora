## The run
Waves of 1-8 operations start together (`Promise.all`) on a clock only the runner moves (hours, sometimes 1-3 days). Operations: create (an instant-book and a request listing, 5 guests, dates in a 9-day window so they overlap a lot), three guests asking for the same nights at once, replaying an earlier idempotency key, host accept / decline, guest cancel, host cancel (often with a second, competing change to the same reservation in the same wave), and a sweeper pass. 1,000 operations = 1,000 of these; each wave is followed by one more sweeper pass.

## What is asserted (zero tolerance)
- **Before the sweeper, after every wave:** (a) no night has two owners; (b)/(d) every reservation that holds nights has exactly its nights and its hold; (c) no ledger row belongs to a reservation that released its nights or to none. The only thing excused is a request whose hold has run out and that the sweeper has not looked at yet (T05 documents that state).
- **After the sweeper:** all of the above for every reservation, with no exception.
- **Independently of the ledger:** two reservations that hold nights never overlap on one listing.
- **The sweeper is never the thing that makes data consistent:** it must report no orphan ledger rows to delete.
- Replaying a key returns the original reservation and never creates a second one.
- The only errors are the services' own 4xx refusals (nights taken, invalid transition, ...); any other error fails the run.
- The run must really have done work (created > 80, nights refused > 20, expiries and completions by the sweeper, every main status reached).
A failing run prints its seed and the last waves; repeat it with `STRESS_SEED=<n>`.

## Does the suite catch bugs? Yes
A planted bug (the ledger's `releaseNights` doing nothing every 7th call) fails seed 1 at wave 22 with "(c) 3 ledger row(s) for cancelled_by_host reservation ..." before the sweeper, and the sweeper reports 3 orphan rows. Four more tests feed the invariant checker deliberately broken data (leftover row, missing row, duplicate night, overlapping reservations) and expect it to report each.

## Decision on the T07 note
T07 asked whether invariant (c) may allow ledger rows of `completed` reservations. It does (ADR-004 keeps past rows; `holdsNights("completed")` is true in `stateMachine.js`). The suite checks that a completed reservation still has exactly its nights.

## Limitations
- The fakes do not model the database's index build, transactions or network delay; only the real-database test does.
- Prices are not checked here (that is `pricing` and `reservations` unit tests): the stress run is about nights and statuses.
- Host blocks and host-calendar edits are not part of the random mix.
