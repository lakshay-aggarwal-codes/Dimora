## Password change
Needs the current password (checked with the plugin's `changePassword`, so wrong guesses count towards the account lock of P02-T02 and a locked account is told "Wait a few minutes"). The new password follows the signup rules, must be typed twice and must differ from the current one. After success the session is renewed with `req.logIn` (a new session id). Plugin and driver error text never reaches the page; an outage is an error page, not "wrong password".

## Account deletion
**Needs:** the member's password (also counted by the lock) and the word `DELETE`.
**Refused, each with its sentence on the page and a code:**
| Code | When |
|---|---|
| `guest_confirmed` | a confirmed stay as guest with check-out after today (a stay in progress counts) |
| `guest_pending` | a request as guest whose hold is still running |
| `host_confirmed` | a confirmed stay at one of the member's places with check-out after today |
| `host_pending` | a request waiting for the member's answer (hold still running) |
| `last_admin` | the member is an administrator and no other active administrator exists |
Past stays, completed stays, lapsed requests and declined / expired / cancelled bookings do not block.
**Order of work:** password check -> blockers -> unpublish the member's published listings (no new request can arrive) -> blockers again (a booking may have landed in between: if so the listings are published again, nothing else changes, and the member is refused) -> one update, applied only to a still-active account, that anonymises it (if it fails the listings are published again) -> delete saved stays (`Wishlist`, `WishlistItem`) and notifications, relabel reports about the account "Deleted user", delete the avatar image (best effort; a failure does not undo the deletion).
**The anonymised account:** `username` = `deleted-<id>`, `displayName` = "Deleted user", `email` = `deleted-<id>@deleted.invalid`, `bio` empty, `avatar` removed, `emailVerifiedAt` null, `status` `deleted`, `hash` and `salt` replaced by random values nobody knows, failed attempts 0. Role is untouched. A test checks the stored document contains none of the old username, email, display name, bio, avatar URL or file name, hash or salt.
**What stays:** reviews (author shown as the deleted account), reservations and their snapshots, messages, reports made by the member, audit rows. The public profile `/users/:id` is a 404 (it already only shows active accounts). Sessions on other devices stop working because the session stores the old username. The old username and email can be registered again.

## Limitations
- After a password change other devices stay signed in: sessions are not listed per member, so they cannot be ended (a `passwordChangedAt` check in the session middleware would fix this; not built).
- A member must cancel or wait out confirmed stays and answer requests themselves; deletion never cancels anything for them.
- Messages the member wrote remain visible to the other person in the conversation, labelled with the deleted account.
- Audit rows keep the admin's account id (an administrator can only delete themselves when another administrator exists).
- No email is sent (P02-T05 is not built), so there is no "your account was deleted" mail and no way to restore.
- Anonymising cannot be undone; there is no grace period.

## Manual checks (owner)
1. Account menu > Account settings. Change the password with a wrong current password (message), then correctly; log out and log in with the new one.
2. With a confirmed future stay (as guest) or a pending request on your listing: the delete section lists why it cannot be done; the account stays.
3. With nothing open: type your password and DELETE: you are logged out; your listing is unpublished; your old reviews show "deleted-..."; the old password no longer logs in; the username can be registered again.
