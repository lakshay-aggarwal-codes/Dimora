## Migration 002
- Reads users with a projection (never `hash`/`salt`), plans in a pure function, then writes with `bulkWrite` (batches of 500).
- Per user: lower-case/trim `email` (update matches the email it read, so a concurrent edit is not overwritten); `displayName` = username if empty; `role: "member"`, `status: "active"`, `bio: ""`, `emailVerifiedAt: null` where missing; `createdAt` from the `_id` timestamp and `updatedAt` = `createdAt` where missing. Then `createIndex({ email: 1 }, { unique: true, name: "email_1" })` (same name/spec Mongoose requests, so no conflict).
- **Duplicates** (same address ignoring case/spaces) and users with no usable email: real run writes nothing and throws a message listing user ids and usernames (no emails); dry run logs `PROBLEM:` lines and returns `duplicateEmailGroups`, `usersWithoutEmail`, `wouldBlock`. Nothing is deleted or merged; the fix is manual (steps in `docs/MIGRATIONS.md`).
- Idempotent: a second run updates 0 documents.

## Limitations / deviations
- Roles are `member` and `admin` only (admin is used from P14-T01).
- No collation on `username` (roadmap: "if desired"); `avatar` is not backfilled (absent until upload); the email format check in the model is deliberately simple (Joi comes in P02-T02).
- `suspended` is stored but not enforced at login yet (P02-T02).
- Duplicate-email signup message reveals that an address is registered; P02-T02 replaces it with neutral wording.
- Existing users loaded before the migration runs still get `role`/`status`/`bio` defaults from Mongoose, so login works either way; the unique index is only guaranteed after the migration.
