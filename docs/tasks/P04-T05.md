# P04-T05 - Publish lifecycle + Host Readiness Checklist (Q30)

Date: 2026-10-17 - Deps: P04-T02 (Q29, the uploaded `Dimora_P04-T02.zip`, applied on top of the repo up to Q28/Q25) and P04-T03 (Q28), present. No new dependency, no env key, **no migration** (one optional model field).

## What was added
| Item | Notes |
|---|---|
| `src/services/readiness.js` | `evaluateReadiness(listing, { minPhotos, minDescriptionChars })` returns `{ score, canPublish, checks }`. Eight items: at least 5 photos; description of at least 200 characters (trimmed); street, city and country present, a map point, and not flagged `needsReview`; guests >= 1 and beds >= 1; a positive integer nightly price (paise); written house rules or `noSpecialRules === true`; check-in and check-out as HH:MM; a cancellation policy from the list. `score` is the share of items done and equals 100 only when `canPublish`. Defaults (5, 200) live in `src/config/constants.js` (`READINESS`). Missing data never throws. |
| `src/services/lifecycle.js` | `publishListing` (draft or unpublished -> published, only if the checklist passes, else `NotReadyError` listing what is missing; a published listing is left alone; deleted or odd statuses refused), `unpublishListing` (published -> unpublished, immediate), `softDeleteListing` (sets `deletedAt`, hides it; refused with a 409 while the night ledger has an upcoming reservation; repeating is harmless). |
| `src/services/ledger.js` | New `hasUpcomingReservation(listingId, { now, timeZone })`: reservation rows from today (in the listing's time zone) on; expired holds and host blocks do not count. |
| `src/utils/visibility.js` | `publicListingFilter()` / `isPublic()`: published and not deleted. Used by the listings page, the home page, the detail page and review posting. |
| Routes/controllers | `GET /host/listings/:id/status`, `POST /host/listings/:id/publish` (now also for unpublished listings), `POST /host/listings/:id/unpublish`; `DELETE /listings/:id` is a soft delete (a blocked delete returns to the status page with the reason). Wizard order checks still run first, so a draft with unfinished steps is sent to the step, one with a short checklist to the step that fixes the first missing item. |
| Preview | `/listings/:id?preview=1`: only the host sees it, with host controls hidden and a banner; anyone else (visitor, other member, admin) gets a plain 404, which does not reveal that the listing exists. Without the parameter, a draft or unpublished listing is still seen by its host (with a notice and a link to the status page) and an admin; to others it looks missing, as before. A deleted listing is missing for everybody. |
| Views | `views/partials/readiness.ejs` (score, progress bar, each item "done"/"to do" in words, a fix link: the wizard step for a draft, the edit page otherwise), `views/host/status.ejs` (state badge, checklist, preview, publish/unpublish, delete with a confirmation dialog), the wizard review step shows the same checklist and keeps Publish disabled until it passes; wizard step 5 has the "I have no special house rules" checkbox (`noSpecialRules`; written rules clear it). |
| Review posting | A review cannot be posted on a draft, unpublished or deleted listing (404). Existing reviews stay in the database when a listing is soft deleted. |

## Limitations / deviations
- Readiness checks that things are **present**, not good: nonsense text of 200 characters passes; the score is progress, not quality. The defaults for check-in/out times and cancellation policy count as chosen (they cannot be told apart from a choice); the wizard's required fields make the host choose them for new listings.
- "Address confirmed" means the address fields are filled, the map found a point, and the old "needs review" flag is off; the explicit confirm-on-map step arrives with P04-T04.
- A listing published through the old single-page form has no `noSpecialRules` and a rough address, so it fails the checklist if it is ever unpublished and republished; its fix links point to the old edit page until P04-T04 reworks it. Nothing changes for listings that stay published.
- Delete is soft: photos stay in Cloudinary and the row stays in the database (a purge job is not part of this task). Reservation creation (P07-T05) does not exist yet, so the "upcoming reservation" block is tested against ledger rows only.
- The legacy `/listings/new` form and `POST /listings` still publish immediately without the checklist (kept for existing tests; P04-T04 retires them).
