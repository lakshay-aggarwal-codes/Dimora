## How the suggestions are chosen
1. The ledger's free stretches between 14 days before the asked check-in and 14 days after the asked check-out (never before today) are read with `availableRanges` (a host block is taken, an expired hold is free).
2. Every start date that fits a free stretch is a candidate: the same number of nights, not the asked stay itself. Candidates are ordered by distance from the asked check-in, earlier first on a tie.
3. Candidates are taken one by one, skipping any that overlaps one already chosen, so the three suggestions are three different stays. Each must pass the booking rules (minimum/maximum stay, notice, same-day cut-off, capacity, not in the past) and is then priced by `getQuote` (the same call as the panel and the checkout), which checks the ledger again. A candidate the quote refuses is dropped and the next is tried. At most 3; none is a normal answer, not an error.
- Only when the nights are taken (`nights_unavailable`): a stay refused for a rule (too short, too many guests) gets no suggestions, because moving the dates would not fix it.
- A suggestion can be booked by someone else before the guest clicks; the checkout then answers with the normal conflict (409), as for any stay.
- **The link**: each suggestion is `/listings/:id?in=...&out=...&guests=...`, an ordinary page address, so it works with the date picker's own `?in=&out=` start and needs no script. (The panel itself needs JavaScript, as before.)

## Search: "Available ±3 days"
A checkbox in the search form (`flex=3`, only the value 3 is accepted; anything else shows "Flexible dates can only be 3 days either side." and is ignored). It needs both dates. A listing stays in the results if any stay of the same length starting from 3 days before to 3 days after the asked check-in is free in the night ledger, and never before today. The map data (`/api/search/map`) uses the same filter, a chip "Available ±3 days" shows it (removing the dates chip removes it too) and pagination, sort and the filter panel keep it. Like the plain date filter, it looks at nights only (not at minimum stay or notice); result cards still link to the listing with the asked dates, where the panel then offers the free ones.

## Property test
`tests/unit/flexibleDates.test.js` makes 500 random busy calendars with random rules (minimum/maximum stay, notice, capacity), requested stays and guest counts, and checks every answer against a brute-force oracle (try every shift from -14 to +14 days, apply the rules, choose greedily) and, for each suggestion: same length, within 14 days, not the asked stay, not in the past, no night taken in the ledger, no rule problem, `getQuote` says bookable, suggestions do not overlap, at most 3.
