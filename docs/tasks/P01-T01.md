# P01-T01 — Config module and fail-fast env validation (Q4)

Date: 2026-10-14 · Node v22.22.2

## Files changed
- `src/config/env.js` (new) — Joi validation of `NODE_ENV`, `PORT`, `MONGODB_URI`, `SESSION_SECRET`, `CLOUDINARY_*`, `MAPBOX_SERVER_TOKEN`, `MAPBOX_PUBLIC_TOKEN`, `APP_BASE_URL`, `DNS_SERVERS`. Exports `validateEnv(source)` (pure, throws `EnvValidationError`, never exits or logs), `loadEnv()` (memoised validation of `process.env`) and `resetConfigCache()`.
- `app.js` — loads config first; on failure prints a readable list and exits 1. Port, DB URL and session secret come from config; the hard-coded secret `mysupersecretcode` is gone; `dns.setServers` now runs only when `DNS_SERVERS` is set; `dotenv` runs with `quiet: true`; `res.locals.mapPublicToken` added.
- `cloudConfig.js`, `controllers/listing.js` — read Cloudinary / Mapbox server token from config instead of `process.env`.
- `views/listings/show.ejs` — browser map token now comes from `mapPublicToken` (the public token), not the server token.
- `.env.example` — rewritten: every key, comments, no values.
- `tests/unit/env.test.js` (new) — 28 unit tests.
- `docs/PROGRESS.md`, `docs/tasks/P01-T01.md`.

## Behaviour
- Missing or blank key → its own message (`X is missing`), all problems listed together. Messages never contain secret values.
- Production: `SESSION_SECRET` ≥ 32 chars and not a placeholder; `APP_BASE_URL` required; `CLOUDINARY_API_SECRET` placeholder rejected; an `sk.` token as `MAPBOX_PUBLIC_TOKEN` is an error (warning outside production).
- The old committed secret `mysupersecretcode` is rejected in **every** environment.
- Old variable names (`ATLASDB_URL`, `CLOUD_NAME`, `CLOUD_API_KEY`, `CLOUD_API_SECRET`, `MAP_TOKEN`) are still accepted with a `[config]` deprecation warning so an existing `.env` keeps working. New names win when both exist. `MAP_TOKEN` fills both Mapbox tokens until P06-T01 splits them.

## DB / config changes
No database changes. New env names (see `.env.example`); **new required value: `SESSION_SECRET`**.

## Commands run and results
- `node --test tests/unit/env.test.js` → 28 pass, 0 fail.
- `node --check` on `app.js`, `cloudConfig.js`, `controllers/listing.js`, `src/config/env.js` → OK.
- `NODE_ENV=production node app.js` without `SESSION_SECRET` → exit 1, message "SESSION_SECRET is missing".
- Empty environment → exit 1 listing all 7 missing keys. Old secret → exit 1.
- Valid env (legacy names) → config accepted, 6 deprecation warnings, then the app proceeded to the DB step (unreachable DB in the sandbox).
- End-to-end probe of the real `app.js` with stubbed DB/auth/Cloudinary and the new env names: login works, pages render, the public Mapbox token appears in the show page and the server token does not. Existing defects (D-02, D-03, …) are unchanged, as expected.
- Not executed: a real Atlas/Cloudinary/Mapbox run (no credentials).

## Limitations / deviations
- Deviation: legacy names accepted as a fallback (not in the roadmap) so your current `.env` does not break; remove later.
- `npm test` is still the default stub (scripts arrive in P01-T02, Jest in P01-T08). Tests use Node's built-in runner for now and will be ported.
- `src/` contains only `config/` for now; the rest moves in P01-T03.
- If the old `dns.setServers` hack was what made Atlas connect on your network, add `DNS_SERVERS=8.8.8.8,1.1.1.1` to `.env`.
- Cookie flags and session store behaviour are untouched (P01-T09).

## Owner actions (DoD+: rotate the secret)
1. The old session secret is public in the repo history; it is now rejected. Generate a new one: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"` and put it in `.env` as `SESSION_SECRET=`.
