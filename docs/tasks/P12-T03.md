## What it does
**Editing (author).** For `REVIEW_EDIT_DAYS` after posting (from `createdAt`; a review without one is dated by its id) the author can change the rating and the comment.
- `PUT /listings/:id/reviews/:reviewId` - guards: login, `authorize("review:edit")` (author only; an admin gets 403, they hide instead), `validateReviewEdit` (rating 1-5, comment 1-2000, optional `from` = `listing|trip`; any other field is a 400).
- `services/reviews.edit`: input is validated first, then the review is read for clear answers (not yours / other listing / hidden / missing = the same 404; past the window = 409 `review_edit_window_closed`). The write is **one compare-and-set** (`author`, `status != hidden`, `createdAt >= now - window`) with `new: false`, so it returns the review as it was; the listing totals then move by `new - old` in **one atomic update** (`ratings.changeRating`, same pipeline style as P12-T02). If that update fails the review is put back (text, rating and the old `editedAt`); if the review was hidden while the totals were being changed they are recomputed from the reviews. Unchanged input writes nothing ("No changes."). A comment-only edit does not touch the totals.
- The review gets `editedAt`; pages show "Edited". The old text is not kept.

**Replying (host).** The listing's owner writes one public reply per review.
- `POST /listings/:id/reviews/:reviewId/reply` (`reply[text]`, 1-1000 characters; posting again replaces it, the first date is kept, `editedAt` is set) and `DELETE` on the same URL to remove it.
- Policy `review:reply` is decided on the **listing** (owner only; not an admin, not the guest). `authorize()` got a small option for this: `authorize("review:reply", { resource: "listing" })` loads the listing and leaves it on `req.listing`.
- A hidden review has left `listing.reviews`, so it cannot be replied to (404); a reply goes out of sight with its review. Reply text is plain text, escaped in views.

**UI.** Listing page review cards: "Edit your review" (`<details>`, prefilled stars and comment, new partial `views/partials/review-edit-form.ejs`), "Response from the host", and for the host "Reply to this review" / "Edit your reply" / "Remove reply" (`views/partials/review-reply-form.ejs`; hidden in the guest preview). Booking page (`/trips/:id`): the guest sees their review with an edit form while editable (returns to the booking), the host's reply and "(edited)".

**Found while doing it (small fix included).** `REVIEW_WINDOW_DAYS` was documented (P12-T01) and validated, but `app.locals.reviewWindowDays` was never set in this repository, so the setting was ignored (the code fell back to 30). `src/app.js` now sets `reviewWindowDays` and `reviewEditDays` from `config.reviews`.

## Limitations
- The previous review text is not kept; there is no edit history.
- No notification to the guest when the host replies (P11 could wire it; not in this card).
- A reply cannot be reported separately; moderation hides the whole review (and so its reply).
- One reply per review; replying to a reply is not possible.
- `trips.service.test.js` "describeReview ... done" expects `hidden: false`, which `describeReview` no longer produces; that failure was there before (lost in an earlier merge) and is untouched. I only added the new fields to its expectation.
- The listing page loops over `listing.reviews`, not the sorted `reviewList` the controller passes, so newest-first is not applied in the view (pre-existing; part of the failing tests from P12-T02's note).

## Deviations
The roadmap card is one line. Choices made: edit window 7 days from posting (configurable), one reply per review, host-only, replace/remove allowed, no edit history.

## Manual checks (owner)
1. As a guest with a recent review: listing page > "Edit your review" > change stars and text > Save. The card shows "Edited", the listing's summary moves by the difference; "Your trips" shows the same.
2. Wait past `REVIEW_EDIT_DAYS` (or set it to 1 and back-date `createdAt` in the database): no edit form; a hand-made PUT gives 409.
3. As the host: "Reply to this review" > post. Everyone sees "Response from the host". Edit it, then "Remove reply".
4. As another member or the guest: no reply tools; a hand-made POST to `/reply` is a 403.
5. As an admin hide the review (Admin > Reviews): it disappears with its reply; editing it as the author gives a 404.
