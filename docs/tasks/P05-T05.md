# P05-T05 - Empty results and suggestions (Q39)

Date: 2026-10-18 - Deps: P05-T02 (Q36), in the uploaded repo. No migration, no new dependency.

## What changed
| Item | Notes |
|---|---|
| `src/services/suggestions.js` (new) | `suggestForEmptyResults({ Listing, parsed, takenIds })` and `popularDestinations(Listing)`. A filter *group* is one thing a visitor sees as one filter: dates (`in`+`out`), amenities, price (`minPrice`+`maxPrice`), type, guests, instant book, room type, bedrooms, words, destination. For each active group (first 4 in that order) it counts the public listings that match the search without that group; the taken-night exclusion stays except when the dates are the group dropped. A group whose count is 0 is never offered. Offered groups are sorted by count (most stays first), at most three, each with a ready link (`listingsUrl` with those parameters removed, the rest kept). |
| Popular destinations | One query over the newest 200 public listings, grouped by `cityKey`; at most six, busiest first. The link uses the city as written (`?dest=Panaji`) only if searching for exactly that text finds the city's own key; otherwise the normalised key. The link carries no other filter, so it has results by construction. |
| Query budget | At most 5 extra queries: up to 4 counts + 1 for destinations (the constant `MAX_EXTRA_QUERIES = 5`; a test asserts the real counts with every filter active). |
| `src/controllers/search.js` | Keeps the list of taken listing ids and, when `total === 0` and a filter is active, calls the service and passes `suggestions` to the view. |
| `views/listings/index.ejs` | "Try this instead" (label, number of stays, link), "Popular destinations", and the empty-state button: "Clear all filters" when there are stays, "List your place" when the site has none. Without `suggestions` (older tests, no filter) it renders exactly as before. |
| CSS, test helper | `.suggestions` styles; `tests/helpers/listingSearch.js` chain gets `select` and `lean` (the destinations lookup). |
| Tests | `suggestions` (unit, 15), `listings.empty` (page with a stubbed model, 8), `search.suggestions.db` (real MongoDB: for eight empty searches it opens every suggestion link on the page and asserts each shows stays). |

## What "never offers a dead end" rests on
1. A filter suggestion is built only from a count that is greater than 0, computed with exactly the filter the link will produce (same `buildFilter`, same taken-night list).
2. A destination link has no other filter and comes from a city key of a public listing.
3. The DB test follows every link the page offers and checks it shows stays.

## Limitations
- Only the first four active groups are looked at (priority order: dates, amenities, price, type, guests, instant book, room type, bedrooms, words, destination). With five or more active filters a later one can be the real cause and not be offered; the destinations and "Clear all filters" still lead somewhere.
- `minRating` and `sort` are not groups: they do not change the results yet.
- Counts ignore the 12-per-page paging (they are totals) and use the stay dates only through the ledger list the page already has.
