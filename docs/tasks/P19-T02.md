
## Demo accounts (demonstration only)
| Role | Username | Email (never resolves) |
|---|---|---|
| host | `dimora_demo_host` | `demo-host@dimora.invalid` |
| guest | `dimora_demo_guest` | `demo-guest@dimora.invalid` |
| guest 2 | `dimora_demo_guest2` | `demo-guest2@dimora.invalid` |
| admin | `dimora_demo_admin` | `demo-admin@dimora.invalid` |

Passwords are random (24 characters), made when an account is created or rotated, **printed once and stored nowhere** (not in code, not in the zip, not in this file). So none is shared between accounts or reused elsewhere. If you lose one: `--rotate-passwords`. The host account is the same one `npm run seed` uses. The admin gets its role through `promoteToAdmin` (audit row `cli:make-admin`), like `npm run make-admin`.

## What the data contains
- **29 published places** (the sample places, upgraded): 5 photos each, street (invented), capacity, cleaning fee, rules, cancellation policy (flexible/moderate/strict), instant-book on about half, amenities, a 200+ character description, weekend price on city and beach places. All pass the Host Readiness Checklist.
- **14 bookings**, one place each: pending 2 (one per guest), confirmed 2 (one instant, one accepted by the host), declined 1, expired 1, cancelled by guest 1 (inside the 5-day window of a moderate policy: partial refund recorded), cancelled by host 1 (full refund, host cancellation counter 1), completed 6.
- **4 reviews** on completed stays; one finished stay is still inside the review window with no review (the "Write a review" button shows for the demo guest), one is past the window.
- Bookings are made by the real services with a set-back clock; `createdAt` of each booking and review is set to the time it was "made" so the refund rules and pages read sensible dates.

## Guards
- `NODE_ENV=production`: refuses (checked in `main` and again in `runDemoSeed`).
- A database that is not on this computer (`mongodb+srv`, any non-localhost host): refuses unless `--yes`. The target is printed first, never with credentials.
- Everything is validated against the real `Listing` model before anything is written.
- `--reset` touches only the demo host's places and what references them (bookings, night ledger, host blocks, reviews, saves, listing stats, conversations and messages). Other users' data is left alone (tested).

## Evidence

This caught one real bug (a borrowed photo on a host the CSP blocks), fixed.

## Limitations and notes
- The two waiting requests hold their nights for 24 hours; then the sweeper expires them. `--reset` makes fresh ones.
- Extra photos are borrowed from other sample places (same setting first), not photos of that place; replace them with real uploads for a polished demo. Only `images.unsplash.com` is used for them because the CSP allows nothing else.
- Found, not changed: the sample cover of "Art Deco Apartment in Miami" is on `plus.unsplash.com`, which the CSP does not allow, so that one cover is blocked in a browser.
- `npm run seed` run after `seed:demo` overwrites the richer fields (photos, pricing sub-fields) of the shared places with the simple sample; run `seed:demo` last.
- No notifications, conversations or saved stays are created; no emails are sent. Payments are simulated as everywhere.
- A place whose nights are already taken in your database is reported (`NOT CREATED - <key>: <reason>`, exit code 1) and the rest still goes in.
- Dates use the listings' time zone (Asia/Kolkata, ADR-008) for every place.
