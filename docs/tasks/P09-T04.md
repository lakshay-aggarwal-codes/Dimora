## Rules
- Only the **guest** of the booking (`reservation:modify`). Host, admin, strangers, missing and malformed ids: the same 404. Suspended guests: 404.
- Allowed while the booking is `pending` (hold still running) or `confirmed`, and the stay has not started (now < check-in time on the listing's clock). Otherwise 409 with a code: `not_modifiable`, `hold_expired`, `stay_started`.
- The place must still be public (`listing_unavailable`, 409). The number of guests stays the same.
- The new dates pass the same `bookingProblems` as a new booking (window, min/max nights, capacity, advance notice, same-day cut-off). Same dates = `no_change` (400); bad or non-text dates = `invalid_dates` (400).
- Nights taken by someone else (or blocked) = `nights_unavailable` (409). The booking's own nights never count against it.
- **Price**: `pricing.quote` for the new dates at today's prices; difference = new total - old total (negative = cheaper). The guest sees it first; the confirm form carries the total they saw, and a different server total is a `PriceChangedError` (409, nothing changed, page shown again). Stored: `pricingSnapshot` replaced by the new quote, one `modifications[]` entry (from, to, difference, currency, reapproval) and a `statusHistory` line (`from == to`, actor guest, note with both ranges). **No money moves.**
- **Pending request**: it stays `pending`, the 24 h hold restarts (reservation and every night), and the host is told "Request changed, please answer again" (re-approval). **Confirmed stay**: stays confirmed, the host is told (`reservation.modified`).

## Ledger order (ADR-004 section added)
1. `reserveNights` for the added nights only (new minus old), all or nothing: a conflict changes nothing.
2. Pending only: `extendHold` for the kept nights.
3. Compare-and-set on the reservation (status, old check-in/out, and a running hold for pending). One of two concurrent changes, or a change and a cancel/accept/expiry, wins.
4. `trimNights(id, newNights)`: the old nights are given up.
Loser of step 3, or an error in step 2/3: `releaseNightsOn(id, added)` removes exactly what step 1 added. If step 4 fails the change stands and the old nights stay blocked (safe side, logged); `trimNights` is idempotent. Sweeper orphan removal only looks at rows of missing/released reservations, so in-flight added rows of a live booking are safe, but leftover rows after a failed trim are **not** cleaned automatically.

## Limitations and deviations
- The roadmap says only pending requests need host re-approval. A **confirmed** stay on a request-only place keeps its confirmation after a change (the host is told and can cancel); a stricter rule would need a new state.
- The guest count cannot be changed here (dates only). Today's prices apply to the new dates, so the difference can include a price change since booking.
- Native `<input type="date">` is used, not the booking-panel date picker; the server is the authority for every rule.
- Refund rules on a later cancellation use the new snapshot; the strict-policy grace period still counts from the original `createdAt`.
