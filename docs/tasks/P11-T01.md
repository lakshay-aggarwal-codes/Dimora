## Behaviour
- `notify` writes one row for exactly the id given. It never looks anyone up; who is told is the caller's decision (P11-T04). Bad input (bad id, type not like `reservation.requested`, missing/over-long text, control characters, a link that is not a same-site path or is `/login`/`/signup`, unknown reference kind) throws `ValidationError` and writes nothing. Payload keys other than `title`, `body`, `url` are dropped.
- Every read and update includes `user` in its filter. Another member's notification and a malformed or unknown id give the same 404.
- Reading sets `readAt` and `deleteAfter` (+30 days); the TTL index removes the row then. Marking again changes nothing. Unread rows are kept until read.
- The count endpoint answers 401 JSON to a visitor, `{ "unread": n }` with `Cache-Control: no-store` otherwise. The user is always the session's; nothing in the query is read.
- Bell: asks at once, then every 30 s while the tab is visible; stops while hidden and asks again when it returns; stops for good on 401. Accessible name is text ("Notifications, 3 unread"); the badge is a visual only. Without JavaScript the bell still links to the inbox.
- Inbox: unread rows say "Unread" in words; titles and texts are escaped; "Mark all as read" appears only when something is unread; the redirect after marking keeps `show` and `page` and nothing else from the request.

## Limitations
- Nothing creates notifications yet; P11-T04 calls `notify`. It should wrap the call so a failure cannot break a booking, and will need a de-duplication key for events that can fire twice (for example the sweeper's "check-in tomorrow").
- Opening a notification's link does not mark it read (only the button does).
- Unread rows never expire. The TTL monitor runs about once a minute, so a read row can outlive its date briefly.
- Test fake `tests/helpers/fakeNotificationModel.js` stands in for the model; query shapes were not run against MongoDB.
- The `.nav-icon-btn[aria-disabled]` CSS rule from the old placeholder is now unused.
