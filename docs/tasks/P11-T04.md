Texts are plain and use only what the recipient may know (listing title from the booking's snapshot, dates, the reason given). Titles and reasons are flattened to one line and cut to the notification limits. Every payload is checked against the real notification service in `tests/integration/notificationEvents.db.test.js`.

## Where the hooks are
- `src/services/reservations.js`: new optional dependency `notifier` (none by default, so a service built in a test sends nothing); the exported instance gets the real one. One `tell()` after a successful create and after a successful transition (after the ledger step). A repeated create (same idempotency key) and every refused or lost-race change send nothing.
- `src/services/sweeper.js`: new step 5, `remind`, only when a `notifier` is passed (`server.js` passes it). It looks at confirmed bookings whose `checkIn` is tomorrow in the listing's own zone (date-only compare; the query is narrowed by the earliest and latest zones on Earth), claims each with `updateOne({ ..., "reminders.checkIn": { $exists: false } }, { $set: ... })` and sends only if the claim changed one row. The summary gains `reminded` only when the step is enabled.
- `src/services/listingModeration.js`: after a suspend or restore update has succeeded.
- A failed notification is logged and ignored; it never fails a booking, a sweeper pass or an admin action. With no open database connection `dispatch` does nothing (so unit tests that stub models stay quiet and fast).

## Deviations and limitations
- **Instant booking** also notifies the host (`reservation.booked`). The card lists only "requested"; without it a host with instant-book listings would hear nothing.
- **At-most-once reminders.** The claim is written before the notification, so a crash between the two loses that reminder instead of sending it twice.
- Check-in reminders go out on the first sweeper pass after midnight in the listing's zone. A booking made after that for a next-day check-in is announced on the next pass.
- Suspending a listing does not notify guests who already booked it (the bookings stay, as the moderation docs say).
- "Review available" fires when the stay is completed, whether or not the guest is still inside the review window (that rule lives in `services/reviews.js`); a stay completed long ago by a late sweeper would still announce it.
- No dedupe key exists in `notify`; the two events that could repeat (check-in reminder, the transitions) are made once-only by the claim and by the compare-and-set respectively.
- No notification when a message arrives (not in the card), no email (P11-T05).

## Manual checks (owner)
1. `npm test` and `npm run lint`; fix anything the unrun suites reveal.
2. Request a stay on a host-approval listing as a guest: the host's bell shows 1 within a minute and `/notifications` links to `/host/reservations`.
3. Accept it as the host: the guest is told (link opens the trip). Decline another: the guest is told.
4. Cancel a confirmed booking as the guest: only the host is told. Cancel another as the host: only the guest is told, with the reason.
5. Book an instant-book listing: the host is told.
6. Let a request expire (or lower the hold in a test database) and run the sweeper: guest and host are both told.
7. Make a confirmed booking with check-in tomorrow and run the sweeper twice: guest and host each get exactly one reminder.
8. As admin, suspend then restore a listing: the host gets both notices, the first with your reason.
