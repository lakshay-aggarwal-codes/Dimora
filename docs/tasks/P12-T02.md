## Rating totals
`ratingSum`, `ratingCount` and `ratingAvg` (= sum / count, 0 with no reviews) change **only** in `src/services/ratings.js`, as one update pipeline on the listing document: it adds to the sum and count, derives the average from the new values in the same operation, and adds or removes the review id in `listing.reviews`. Nothing is read first, so two reviews written at the same moment cannot overwrite each other's total (a recompute from a stale read could). Totals never go below zero; a rating that is not a whole 1-5 changes the list but not the totals.
- **Write:** `reviews.submit` stores the review, then runs that one update. If the update fails the review is deleted again, so a review never exists without being counted.
- **Delete:** `reviews.remove` (used by the delete route, and later by admin moderation) deletes with `findOneAndDelete` and subtracts only if this request actually deleted it: two simultaneous deletes subtract once. If the subtraction fails the totals are repaired from the reviews (`recomputeRatings`).
- **Migration 009** gives every listing `ratingSum` and makes the other two agree with the reviews it holds; listings already right are not written; a dry run only counts.

## UI
- **One form, two places:** `views/partials/review-form.ejs` (rating fieldset with legend, five stars, none pre-selected, required, message under the stars from `script.js`, comment up to 2000 characters, hidden reservation id). The listing page uses it with ids `first-*`, the booking page with ids `trip-*` so a page never has duplicate ids.
- **Booking page (`/trips/:id`), for the guest of a completed stay:** the form with the last day to review, or the review itself (stars, comment), or "The time to review this stay ended on ...". Hosts and admins see none of this.
- **Your trips:** a finished stay inside the window shows "How was your stay? **Write a review**"; a reviewed one shows "You reviewed this stay." (one extra query per page, only when the page has finished stays).
- **Listing page:** reviews newest first (a review without a date is dated by its id), each with month and year; the summary comes from the stored totals ("Rated 4.7 out of 5 from 10 reviews"); a listing without totals yet is counted from its reviews. `ratingSummary` had never been passed to the view (the view fell back to "no reviews"); it is now.

## Limitations
- Aggregates exist per listing only; hosts' dashboards (P13) and trust indicators (P12-T05) will read them.
- Editing a review is P12-T03 (the totals pipeline would then add and remove in one update).
- Deleting a review frees its stay to be reviewed again inside the window.
- The listing page shows every review (no paging yet); the card sorts newest first.
- Concurrency is proven by the pipeline's shape and the interpreter, and by the database tests once you run them.
